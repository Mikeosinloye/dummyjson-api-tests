# DummyJSON API Test Automation

An API test automation framework for the public [DummyJSON](https://dummyjson.com) REST API.

It is written in **C#** with **Gherkin** (BDD) scenarios. It covers the nine exercises in the STA coding challenge across four resources: **Auth**, **Users**, **Products** and **Cart**.

After every test run, an **HTML report** is generated at `TestResults/report.html`.

Install these before running the tests:

- **.NET 9 SDK**: download it from https://dotnet.microsoft.com/download
- **Internet access** to `https://dummyjson.com`
- *(Optional)* **Visual Studio 2022** (17.12 or later) or **VS Code** with the *C# Dev Kit* extension

```bash
dotnet --version
```

## 3. How to run the tests

### Option A: Command line (quickest)

**Step 1.** Clone the repository and move into the folder that contains the `.sln` file:

```bash
git clone <repository-url>
cd DummyJsonApiTests
```

**Step 2.** Run all tests:

```bash
dotnet test
```

The first run restores the NuGet packages automatically. A successful run ends with:

```
Passed!  - Failed: 0, Passed: 9, Skipped: 0, Total: 9
```

> **Note:** run `dotnet test` from inside the `DummyJsonApiTests` folder (where the `.sln` file is). Running it from a parent folder gives the error *"MSB1003: Specify a project or solution file"*.

**Step 3.** Open the HTML report that was generated by the test run (see below).

<br>

### HTML report

An **HTML report is generated automatically after every test run**. No extra command or setting is needed. It is saved to:

```
DummyJsonApiTests/TestResults/report.html
```

Open it in any web browser. For example, from the `DummyJsonApiTests` folder:

```bash
# Windows
start TestResults/report.html

# macOS
open TestResults/report.html

# Linux
xdg-open TestResults/report.html
```

The report shows:

- every feature and scenario, with a pass/fail result
- each Gherkin step, with its duration
- the error message for any failed step

The report is overwritten on each run, so it always reflects the latest results. It is git-ignored, so it is never committed.



### Useful command-line options

Run the tests **with step-by-step output** (each Gherkin step and a one-line summary of each HTTP call):

```bash
dotnet test --logger "console;verbosity=normal"
```

Run **one area only**, using its Gherkin tag:

```bash
dotnet test --filter "Category=auth"
dotnet test --filter "Category=users"
dotnet test --filter "Category=products"
dotnet test --filter "Category=cart"
```

Run **a single scenario** by name:

```bash
dotnet test --filter "FullyQualifiedName~DeleteACart"
```

Save a **test results report** (`.trx`, written to the `TestResults` folder):

```bash
dotnet test --logger "trx;LogFileName=results.trx"
```

<br>

### Option B: Visual Studio

1. Open `DummyJsonApiTests.sln`.
2. Build the solution (**Build → Build Solution**, or `Ctrl + Shift + B`).
3. Open **Test → Test Explorer**.
4. Click **Run All Tests**.
5. When the run finishes, open `TestResults/report.html` to view the HTML report.

Each scenario shows up as its own test, grouped by feature.

<br>

### Option C: VS Code

1. Open the `DummyJsonApiTests` folder.
2. Make sure the **C# Dev Kit** extension is installed.
3. Open the **Testing** panel (the flask icon on the left).
4. Click **Run Tests**.
5. When the run finishes, open `TestResults/report.html` to view the HTML report.

Or open a terminal in VS Code and use `dotnet test` as in Option A.

### How the layers fit together

```
Feature file  →  Step definition  →  Service  →  ApiClient  →  DummyJSON API
 (what)            (glue + checks)     (endpoint)   (HTTP)
```

- **To change what is tested**, edit a `.feature` file.
- **To change how a step checks something**, edit the matching file in `StepDefinitions/`.
- **To change an endpoint, route or request body**, edit the matching file in `Services/`.

## 5. Test scenarios

There are **9 scenarios**, one per exercise in the brief.

| #  | Feature            | Scenario                                                   | Endpoint                         |
| -- | ------------------ | ---------------------------------------------------------- | -------------------------------- |
| 1  | `Auth.feature`     | Authenticate a user and store the access token             | `POST /auth/login`               |
| 2  | `Auth.feature`     | Validate Id, first name and last name of the current user  | `GET /auth/me`                   |
| 3  | `Users.feature`    | How many users have red hair                               | `GET /users/filter`              |
| 4  | `Users.feature`    | Add a new user (details, hair, full address)               | `POST /users/add`                |
| 5  | `Products.feature` | Price of iPhone 13 Pro                                     | `GET /products/search`           |
| 6  | `Products.feature` | Get the 15th product using pagination                      | `GET /products?limit=1&skip=14`  |
| 7  | `Products.feature` | Update the title of product 121                            | `PUT /products/121`              |
| 8  | `Cart.feature`     | Add 5 products to a cart, validate total discount %        | `POST /carts/add`                |
| 9  | `Cart.feature`     | Delete a cart                                              | `DELETE /carts/1`                |



Every scenario checks three things:

- the **status code**
- the **response payload**
- the **specific values** the exercise asks for



Where possible, results are also cross-checked against a second, independent source:

- **Red hair:** the filter result is compared with a manual count over the full user list.
- **Cart:** each product's discount percentage is compared with its own product record.
- **Access token:** the token is decoded to confirm it was issued for the logged-in user.
- **Pagination:** the raw response is checked to contain only that one product.
- **Product update:** the new title is returned, and all other fields are unchanged.

## 6. Configuration

Settings are in `DummyJson.ApiTests/appsettings.json`:

| Setting              | Default                  | Meaning                         |
| -------------------- | ------------------------ | ------------------------------- |
| `BaseUrl`            | `https://dummyjson.com`  | API under test                  |
| `TimeoutSeconds`     | `30`                     | Request timeout                 |
| `TokenExpiresInMins` | `30`                     | Lifetime of the login token     |
| `Username`           | `emilys`                 | Login user                      |
| `Password`           | `emilyspass`             | Login password                  |



The login user is DummyJSON's **public demo account**, not a private credential.

Any setting can be overridden **without editing the file**, using an environment variable that starts with `DUMMYJSON_Api__`:

```bash
# macOS / Linux
export DUMMYJSON_Api__BaseUrl=https://dummyjson.com

# Windows PowerShell
$env:DUMMYJSON_Api__BaseUrl = "https://dummyjson.com"
```

Alternatively, create an `appsettings.Local.json` next to `appsettings.json`. It is git-ignored, so local values are never committed.

## 7. Development decisions

**Layered design**

Step definitions never build HTTP requests themselves. They call a service class, and the service owns the endpoint details. If an endpoint changes, the fix is made in one place.


**Reqnroll instead of SpecFlow**

SpecFlow is no longer maintained. Reqnroll is its official open-source successor and uses the same Gherkin syntax.



**RestSharp for HTTP**

The challenge is pure REST, so a lightweight HTTP library is the best fit. One shared client is reused across all tests rather than created per test.



**Independent scenarios**

Each scenario gets its own fresh state, so tests can run in any order. Scenario 2 logs in by itself rather than relying on scenario 1.



**Designed for a mock API**

DummyJSON does not save changes. The add, update and delete scenarios therefore validate the request and the response only. They never expect a change to still be there on a later request.



**Exact decimal comparisons**

Prices and percentages use `decimal` rather than `double`, so values such as `1099.99` and `62.11` are compared exactly.



**Quiet output, detailed failures**

On a passing run, each HTTP call is logged as a single line (method, URL and status code), so the output stays short.

The full request and response bodies are kept in memory and printed **only when a scenario fails**, so the evidence is there exactly when it's needed. Passwords and tokens are always hidden.

Multi-field checks report every mismatched field in one run, not just the first.

<

**Test data in the feature files**

Expected values (e.g. product 15 = *Wooden Bathroom Sink With Mirror*, price 799.99) sit in the Gherkin, so they can be read and changed without touching C#. All of them were confirmed against the live API.

## 8. Assumptions

These are the places where the brief could be read more than one way, and the choice made in each:

1. **Cart "total discount percentage"**
   The API response has no field for this. It is calculated as the **sum of each product's `discountPercentage`**:
   `10.48 + 18.19 + 9.84 + 12.16 + 11.44 = 62.11`

2. **"Response should only contain this product" (15th product)**
   The page holds exactly one product, and `select=id,title,price` limits it to the fields the exercise asks about.

3. **"Delete a Card"**
   Taken to mean *delete a cart*, as it sits under the Cart section.

4. **Login user**
   The brief doesn't name one, so DummyJSON's documented demo user `emilys` is used.

5. **Red hair filter**
   The filter is case-sensitive: `Red` returns 25 users and `red` returns none. The dataset's own casing is used.

6. **Products added to the cart**
   Not specified in the brief, so products 1 to 5 are used, with mixed quantities (8 items in total).
